# บทเรียนการปรับ UI ตาม Mockup

โครงการ: มงคลเวลา / hora-astro
บันทึก: 21 กันยายน 2026
ขอบเขต: รอบปรับ Home, shared header, carousel, daily card, discovery sections และ footer รวมถึงบัคภาพการ์ดและ chip ที่พบระหว่างงานฝั่งวัด และรอบปรับ Planner responsive

เอกสารนี้เป็นแนวทางทำงานรอบถัดไป ไม่ใช่คำรับรองว่าหน้าปัจจุบันเหมือน mockup หรือได้รับอนุมัติครบแล้ว และไม่ใช่รายการให้ย้อนกลับไป redesign ทั้งเว็บไซต์โดยอัตโนมัติ

## ข้อสรุปหลัก

### เพิ่มเติมจาก Shared Header / Navbar

- ความ compact ต้องวัดทั้งพื้นที่ panel, ขนาดหัวเรื่อง, น้ำหนักไอคอน, ความสูงแถว และจำนวนทางเข้าที่ซ้ำ ไม่ใช่ลด padding อย่างเดียว รอบนี้ลด panel วัดจาก 640 เป็น 560px และ title มือถือจาก 24 เป็น 20px โดยยังให้พื้นที่กดอย่างน้อย 44px
- แยก “ปลายทางต้องครบ” ออกจาก “ทุก alias ต้องซ้ำใน drawer” ลิงก์ utility ที่ URL ตรงกับเมนูหลักสามารถรวมทางเข้าได้ แต่ห้ามลบ Day, Hub overview หรือ Commerce ที่ยังมีความหมายแยกกัน
- ตรวจ rendered icon จริง: scoped CSS ของ Astro อาจชนะ parent rule ทำให้ไอคอนกลับเป็น 32px แม้ wrapper ตั้ง 22px และการย้าย owner ของ SVG อาจทำให้ stroke หาย
- ฟอนต์เป็นส่วนหนึ่งของ composition: แยก family/weight/line-height ตามบทบาท และตรวจที่ข้อความชั้นในจริง ไม่ใช่แค่ wrapper เพราะ `:lang(th)` อาจทับ inheritance ได้ ตรวจ font ที่ใช้วาด glyph และ CSS response หลัง build ด้วย รอบนี้พบ token stylesheet 404 จากการ import CSS เดียวกันคนละรูปแบบ ทำให้ fallback โดยที่ build ยังผ่าน
- รอ font หลังเปิด dropdown/drawer อีกครั้ง เพราะบางน้ำหนักยังไม่ถูกโหลดตอนปิดเมนู แล้วตรวจภาพ Desktop/Mobile ด้วยตา น้ำหนักที่เหมาะกับ desktop navigation ไม่จำเป็นต้องเหมาะกับรายการในมือถือ
- Shared navigation ต้องรักษา identity ขณะ CMS refresh ไม่ใช่เพียงนำ HTML มารวมไฟล์เดียว ต้องตรวจ focus, กลุ่มที่เปิด และ scroll รวมถึง SSR/no-JS
- แถบ utility ที่เลื่อนหายกับ main header ที่ sticky เป็นคนละ measurement; popup ใช้ visible bottom แต่หน้า Calendar/anchor ใช้ sticky height
- ภาพเปรียบเทียบต้องจับสถานะเดียวกัน: drawer ที่เลื่อนไปท้ายหลังทดสอบ Tab ไม่ใช่ภาพของสถานะเพิ่งเปิด ต้อง reset scroll ก่อน capture และเปิดดูภาพใหม่เอง

รายละเอียดและหลักฐานรอบนี้: `docs/header-navbar-implementation.md`

ปัญหารอบนี้ไม่ได้เกิดจากผู้ใช้ให้รายละเอียดไม่พอเป็นหลัก แต่เกิดจากการนำแบบไปทำเป็นจุด ๆ โดยอ่าน composition และรายละเอียดของแบบไม่ครบ จากนั้นตรวจว่าโค้ดทำงานได้มากกว่าตรวจว่าภาพที่ได้สื่อดีไซน์เดียวกันหรือไม่

ความรับผิดชอบของผู้ implement คือค้นหาความต่างที่เห็นได้เองทั้งบริเวณที่แก้และภาพรวมในขอบเขตงาน ไม่รอให้ผู้ใช้บอกเรื่องไอคอน ความโปร่ง ขนาดการ์ด ลวดลาย footer หรือ mobile ซ้ำทีละข้อ

หลักที่ต้องจำ: **ยืดหยุ่นวิธีทำ แต่รับผิดชอบต่อเจตนาของแบบและความครบของรายละเอียด**

## หลักการที่ใช้

งานนี้เป็น **mockup-led product adaptation**: ใช้แบบเป็นทิศทางที่ได้รับอนุมัติ แล้วปรับ geometry, component structure, ภาพ และเนื้อหาให้ทำงานกับเว็บจริงได้ โดยยังคงลำดับสายตา ความหนาแน่น บทบาทขององค์ประกอบ และบุคลิกของแบบ

| แนวทาง | สิ่งที่ใช้ตัดสินงาน |
| --- | --- |
| Exact reproduction | ความตรงของคุณสมบัติที่ขอและมีหลักฐานจาก reference |
| Mockup-led adaptation | ผลงานยังอ่านเป็นดีไซน์เดียวกัน รายละเอียดสำคัญไม่หาย และรองรับผลิตภัณฑ์จริง |
| Inspiration only | หยิบ mood หรือแนวคิดมาออกแบบใหม่ได้ ไม่อ้างความตรงกับต้นแบบ |

`reference-to-a-tee` ปัจจุบันมีโหมด faithful adaptation อยู่แล้ว จึงไม่ควรสรุปว่า skill เดิมไม่มีความยืดหยุ่นเลย ความต่างของ `mockup-to-product` คือให้ **การตีความและปรับใช้อย่างมีวิจารณญาณเป็นหลักตั้งต้น** ไม่เริ่มจาก exact parity แล้วแจกแจงทุกการปรับเป็นข้อยกเว้น

เมื่อผู้ใช้ขอ pixel-perfect อย่างชัดเจน ให้ใช้โหมด exact ตามคำขอ ไม่สลับมา adaptation เพื่อหลบความต่างที่แก้ยาก

## จุดที่ทำให้ต้องแก้ซ้ำ

สิ่งที่ผู้ใช้ชี้และผลที่เห็นเป็นหลักฐาน ส่วนสาเหตุในตารางเป็นข้อวิเคราะห์จากลำดับการแก้ ไม่ใช่ผลการทดลองแยกสาเหตุทุกตัวแปร

| จุดที่เกิดขึ้น | สิ่งที่พลาด | วิธีป้องกันและหลักฐานที่ต้องดู |
| --- | --- | --- |
| Banner ใกล้ขึ้นแต่ยังไม่เหมือน | เปลี่ยนโครงและสี แต่ไม่เก็บความสัมพันธ์ระหว่างหัวเรื่อง รูป พื้นที่ค้นหา shortcut และ daily card | อ่านเป็นกลุ่มเดียวก่อน วัดแนวเริ่ม/จบ น้ำหนัก และพื้นที่ว่าง แล้วดูทั้ง hero ไม่ใช่เฉพาะปุ่ม |
| ไอคอน พื้นโปร่ง และขนาด components | มองเป็นของแต่งที่ทำทีหลัง ทั้งที่เป็นส่วนของภาษาดีไซน์ | สำรวจ icon family, fill/stroke, optical size, ผิวทึบ/โปร่ง, border และ shadow ตั้งแต่ก่อนลงมือ |
| มือถือรกและอ้วน | ย่อ desktop แต่ยังใช้ spacing, controls และลำดับเดิม | เขียน composition ของ mobile แยก ทดสอบที่ขนาดจริง ไม่ย่อภาพทั้งหน้าจนตัวหนังสือดูพอดี |
| Carousel ลูกศรลอยและ controls ใหญ่ | แต่ละปุ่มผ่าน แต่ alignment และพื้นที่รวมไม่ผ่าน | ตรวจ bounding box ของทั้งกลุ่ม แนวกลาง optical, counter/dots, pause และพื้นที่ไม่ชนข้อความ ทั้ง touch และ keyboard |
| ข้อความ fade ซ้ำ แต่ผู้ใช้ยังต้องการ animation | สับสนระหว่างวงจรข้อความกับ carousel หรืออาจแก้ด้วยการปิด motion ทั้งหมด | ระบุ element และจังหวะที่ผิด แก้ lifecycle ของ animation นั้น โดยรักษา motion ที่ตั้งใจและ reduced-motion |
| การ์ดหมวดหลักต่างจากแบบ | มีสามการ์ดเหมือนกัน แต่รูปกินสัดส่วนไม่เท่ากัน ข้อความแตกบรรทัด และลูกศรไม่มีพื้นที่ของตัวเอง | ล็อก image frame, ตรวจ image:text ratio, title wrapping และพื้นที่ CTA ด้วยเนื้อหาจริง |
| Footer และลวดลายตกหล่น | แก้เพียงความสูง ไม่เก็บ composition, texture, botanical motifs หรือกลุ่ม CTA | footer ต้องอยู่ใน inventory ของทั้งหน้า ดูรายละเอียดที่ขอบภาพ พื้นหลัง และความสัมพันธ์กับ section ก่อนหน้า |
| Daily card ยังคนละ layout | ใช้ข้อมูลที่มีเป็นตัวกำหนดโครงใหม่ จนหัวเรื่อง วันที่ moon/meta และคำแนะนำไม่อยู่ตามกลุ่มของแบบ | แยกความต่างด้านข้อมูลออกจาก layout ที่ทำได้ ไม่ใช้การไม่มี lucky data เป็นเหตุให้ทุกอย่างเรียงต่าง |
| รูปจริงติดสิ่งกีดขวาง | เลือกภาพจากชื่อสถานที่หรือสี โดยไม่ได้ดูฉากและ crop จริง | เปิดดูภาพก่อนใช้ ตรวจ barrier/scaffolding, subject, gold/green balance และ focal point ทั้งสอง viewport |
| รูปการ์ดยาวแล้วดันทั้งแถว | ปล่อย intrinsic image ratio กำหนดความสูงใน grid | ให้ media wrapper กำหนด geometry และภาพ cover ภายใน ทดสอบ portrait/landscape/fallback |
| ชื่อสถานที่ล้น chip จน X หาย | ไม่แบ่งพื้นที่ข้อความกับ action และไม่ทดสอบข้อมูลยาว | ข้อความต้องยุบหรือ wrap ได้ ปุ่มลบต้องไม่ shrink และยังมี hit area; ไม่แก้ด้วยการซ่อน action |
| Header ต้องกลับมาแก้อีกและต้อง shared | ตรวจเฉพาะหน้าแรกหรือสร้าง style เฉพาะหน้าแทนการแก้ owner | ระบุ shared owner และ consumers จริง ใช้ variant ตามหน้าที่ ไม่บังคับทุกการ์ดเหมือนกัน |
| ต้องทวน overall หลายครั้ง | ตรวจ crop ล่าสุด แต่ไม่ดูผลต่อความสูง จังหวะ และน้ำหนักทั้งหน้า | หลัง batch ที่เปลี่ยน composition ให้ดู full page ทั้ง desktop/mobile; งานเล็กดูเฉพาะบริเวณกับเพื่อนบ้าน |

## สิ่งที่ควรคิดให้ครบก่อนเขียนโค้ด

### 1. อ่านแบบเป็นระบบ ไม่ใช่รายการกล่อง

- **ภาพรวม:** งานหลักของหน้า ลำดับสายตา section rhythm, density, positive/negative space และความสัมพันธ์ header/hero/footer
- **องค์ประกอบ:** ขนาดและสัดส่วน image:text, card footprint, title/meta/actions, รูปแบบแนวนอนหรือแนวตั้ง และตำแหน่งที่ควร center
- **รายละเอียด:** icons, optical alignment, ทึบ/โปร่ง, blur fallback, strokes, shadows, separators, decorative edges และ texture
- **Responsive:** อะไรคงเดิม อะไรย้าย อะไรย่อได้ อะไรต้อง wrap หรืออยู่ใน scroll container และอะไรเปิดภายหลังได้โดยไม่สูญเสียทางไป

ไม่ต้องสร้างเอกสารใหม่ทุกครั้ง งานเล็กจดไม่กี่บรรทัดได้ แต่งานทั้งหน้าต้องมีรายการทุก section เพื่อไม่ลืมส่วนท้าย

### 2. แบ่งสิ่งที่ต้องรักษากับสิ่งที่ปรับได้

| ประเภท | หลักตัดสินในงานมงคลเวลา |
| --- | --- |
| ต้องรักษา | เส้นทางค้นหา/วางแผนจริง, ข้อมูลและ source precedence ของ CMS, semantics, permissions, form behavior, keyboard/touch และการอ่านภาษาไทย |
| ต้องรับมาจากแบบ | hierarchy, กลุ่มข้อมูล, สัดส่วนโดยรวม, ความกระชับ, บุคลิกแดง-เขียว-ทอง, รายละเอียดไอคอนและวัสดุที่ทำให้แบบเป็นแบบนี้ |
| ปรับได้ในขอบเขตที่อนุญาต | ขนาด banner, grid tracks, breakpoint, padding, image crop, ตำแหน่ง controls, component composition และการกระจายข้อความจริง |
| ไม่อนุมานเอง | ฟีเจอร์ใหม่ บัญชีผู้ใช้ใหม่ เส้นทางที่ไม่มีจริง ตัวเลขผู้ใช้/คะแนน/ฤกษ์ดีที่ไม่มีแหล่ง หรือการเปลี่ยนทั้งเว็บที่ไม่ได้ขอ |

การอนุญาตให้รื้อ layout ไม่เท่ากับอนุญาตให้ทำลาย data/UX contract และการรักษา contract ไม่ได้แปลว่าต้องเก็บ geometry เดิมที่ผู้ใช้ขอให้เปลี่ยน

### 3. ข้อมูลจริงไม่ใช่ข้ออ้างด้านดีไซน์

- คงข้อมูลจริง เช่น จำนวนวัด ไม่ใช้ตัวเลข 4,200+, 100K+ หรือ 4.9 ตามภาพโดยไม่มีหลักฐาน
- ถ้าไม่มี field ให้ปรับ balance ของข้อมูลที่เหลือ ไม่ใส่ช่องว่างหรือการ์ดปลอมเพื่อให้จำนวนตรง
- รูป moon และ lunar label ใช้ระบบเดิมได้ แต่ต้องสื่อข้อจำกัดของค่าคำนวณ ไม่ทำให้ดูเป็นข้อมูลโหราศาสตร์ที่ตรวจรับรองแล้ว
- การเปลี่ยน lucky fields เป็น calendar shortcuts เป็น **การเลือกทางออกใหม่** ไม่ใช่สิ่งเดียวกับใน mockup ต้องตรวจว่าหน้าที่ น้ำหนัก และความสูงยังเหมาะ หรือควรตัดแถวนั้นออกในบริบทนั้น
- ใช้ข้อมูลสั้น ยาว และขาดหายตรวจ layout โดยไม่สร้าง backend หรือ CMS field ใหม่เพียงเพื่อเติมภาพ

### 4. ภาพและลวดลายมีหน้าที่ต่างกัน

ภาพ hero ต้องรับใช้ composition จริง: subject ที่เห็นได้ แสงทอง พื้นเขียว พื้นที่ให้ข้อความ และ crop ที่ยังสวยบนโทรศัพท์ การใช้รูปวัดใดก็ได้แล้วคลุมสีเข้มไม่เท่ากับรับ art direction มาแล้ว

Content photography ต้องผ่าน CMS slots เดิมพร้อม alt/focal point/source/license ไม่ hard-code ซ้ำใน template หรือ browser script ส่วน botanical ornament ที่เป็นวัสดุแบรนด์ใช้ asset/component ร่วมได้ ไม่จำเป็นต้องยัดเป็น CMS content ทุกชิ้น

รักษาภาระ attribution ตาม license เสมอ คำว่า demo ไม่ทำให้สิทธิ์การใช้ภาพเปลี่ยน การซ่อนเครดิตในรอบนี้เป็นสิ่งที่ต้องทบทวนก่อน public release ไม่ใช่ pattern ให้โครงการอื่นลอกตาม

### 5. Shared ไม่ได้แปลว่าเหมือนกันทุกหน้า

- Header, icon primitive, circular arrow, carousel controls และวัสดุผิวที่ใช้ซ้ำควรมี owner ชัดเจน
- แก้ consumers ที่อยู่ในขอบเขตจริง ไม่ใช่สร้าง component ใหม่แล้วเหลือสำเนาเก่าใช้งานอยู่
- รักษา variant ที่มีเหตุผล เช่น card แบบ horizontal กับ vertical หรือ Home footer กับหน้าข้อมูล
- การแก้เฉพาะ Home branch ของ `Footer.astro` ไม่ใช่หลักฐานว่า footer ทุก route ได้ดีไซน์ใหม่ ต้องรายงาน scope ให้ตรง
- เมื่อขอ applied across the website ให้ตรวจตัวแทน consumers ของแต่ละ variant และบอก exclusions ไม่อ้างทั้งเว็บจาก screenshot หน้าเดียว

## วิธีทำงานรอบถัดไป

1. **ยืนยันขอบเขตและภาพที่ใช้:** เลือก reference ล่าสุดตามที่ผู้ใช้ระบุ แยก desktop/mobile และบันทึกข้อยกเว้นที่ตกลงแล้ว ไม่ใช้ modification time ตัดสินเอง
2. **สำรวจช่องว่างรอบเดียวให้ครบ:** ทั้งหน้าเมื่อขอทั้งหน้า รวม shell, ภาพ, controls, รายละเอียดตกแต่ง และ footer; ไม่เริ่มเขียนจาก section แรกแล้วค่อยค้นพบที่เหลือทีละรอบ
3. **จัดลำดับแก้:** hierarchy/composition ก่อน แล้ว component geometry และ visual finish เป็น batch ที่สอดคล้องกัน เก็บรายละเอียดที่ยังไม่ทำไว้ ไม่ปล่อยให้หายระหว่างทาง
4. **แก้ที่ owner:** ใช้ tokens/components/variants เดิมที่เหมาะสม รื้อได้เมื่ออยู่ในขอบเขตที่อนุญาต หลีกเลี่ยง override CSS สะสมที่แก้ viewport หนึ่งแล้วทำอีกอันพัง
5. **ตรวจระหว่างทำด้วยข้อมูลจริง:** ภาพแนวตั้ง ชื่อวัดยาว ป้ายวันยาว จำนวนจริง และ CMS override ต้องไม่ทำให้ geometry เปลี่ยนโดยไม่ตั้งใจ
6. **กลับมาดูภาพรวม:** เทียบใน state และ viewport ที่เทียบกันได้ ดู actual-size สำหรับ readability และย่อทั้งหน้าแบบ uniform สำหรับ rhythm ไม่ยืดภาพต้นแบบเพื่อให้ดูตรง
7. **ตรวจและจบตาม risk:** visual evidence กับ behavior evidence แยกกัน แก้ความต่างที่เห็นและอยู่ในขอบเขตเองก่อนส่ง ถ้าเหลือข้อจำกัดให้บอกตรง ๆ ไม่ใช้คำว่าผ่านทั้งหมด

สำหรับ tiny follow-up ไม่ต้องรื้อ inventory, full build หรือวิ่งทุก route ใหม่ อ่าน owner ที่เกี่ยวข้องและตรวจบริเวณปัจจุบันหนึ่งครั้งก็พอ หากขยาย shared contract, CMS, routing หรือ deploy จึงเพิ่ม gate ตามความเสี่ยง

## เกณฑ์ก่อนส่งให้ผู้ใช้ดู

- [ ] เปิดภาพ render ดูด้วยตาของผู้ implement เองแล้ว **ทั้ง Desktop และ Mobile ทุกครั้ง** ไม่ใช่เพียง capture สำเร็จหรือส่งไฟล์ให้ผู้ใช้ตรวจแทน
- [ ] เทียบแต่ละ viewport ด้วย framing/scale ที่ใกล้กัน และเปิดดูขนาดอ่านได้จริง ไม่ตัดสินจากภาพย่อทั้งหน้าเพียงภาพเดียว
- [ ] ไม่มีส่วนในขอบเขตที่หลุดจากการอ่านแบบ รวม mobile และส่วนล่างของหน้า
- [ ] ภาพรวมยังอ่านเป็นดีไซน์เดียวกัน ไม่ใช่เพียงมี section ชื่อเดียวกันหรือสีใกล้กัน
- [ ] icons, translucency, motifs, separators และ optical centering ถูกนำมาใช้หรือมีเหตุผลรองรับการดัดแปลง
- [ ] ความสูงของการ์ด ช่องรูป พื้นที่ข้อความ และ controls อยู่ในสัดส่วนที่ตั้งใจ ไม่ถูกข้อมูลจริงดัน
- [ ] มือถือไม่ใช่ desktop ที่ย่อทุกอย่างจนตัวเล็ก และยังใช้งานด้วย touch/keyboard ได้
- [ ] ตรวจทั้งบริเวณที่แก้และผลต่อ rhythm รอบข้างแล้ว
- [ ] ไม่สร้างข้อมูลปลอม ไม่ซ่อน action เพื่อความสวย ไม่เปลี่ยน CMS source และไม่ตัดสิทธิ์/เส้นทางเดิม
- [ ] Shared-component coverage ที่รายงานตรงกับ consumers ที่ตรวจจริง
- [ ] มีภาพปัจจุบันพร้อมขอบเขต/state ของการตรวจ และระบุ material differences ที่เหลือ
- [ ] Functional tests ผ่านไม่ได้ถูกใช้แทนการตัดสิน visual quality; ยังไม่อ้าง user approval หากยังไม่ได้รับ

## บทเรียนเพิ่มจาก Planner

ผู้ใช้ย้ำเมื่อ 21 กันยายน 2026 ว่าต้องใกล้ mockup ในระดับประมาณ 85–90% ด้วยสายตา ไม่ใช่มี section ครบและให้ผู้ใช้เป็นคนชี้ความต่างอีกครั้ง เป้าหมายนี้ไม่ใช่คะแนนจาก pixel diff, จำนวน test หรือความมั่นใจของผู้ implement และรอบนี้ไม่ได้มีการวัดเปอร์เซ็นต์ความเหมือน

### สิ่งที่พลาดซ้ำ

- ตรวจ flow/state ละเอียด แต่ปล่อย geometry ของทั้งหน้าผิด: แผนที่ถูกกล่องสรุปดันลง ฟอร์ม/toolbar หลายแถวเกินจำเป็น timeline และ selected tray ใช้พื้นที่มาก
- ภาพ comparison เดิมวาง reference ที่มีทั้ง desktop+โทรศัพท์ไว้ข้าง desktop เพียงหน้าเดียว ทำให้ทั้งคู่ถูกย่อคนละสเกล จึงตัดสินสัดส่วนได้ไม่ดี
- คำว่า compact ไม่ใช่ลด padding อย่างเดียว ต้องจัดกลุ่มและน้ำหนักใหม่ เช่น map-first ใน desktop rail, รายละเอียดของ stop เปิดจาก chevron, มือถือพับเฉพาะคำแนะนำ/การจัดการรายการ แต่ยังแสดงผลแผนจริง
- ไอคอนที่มี element ขนาด 20px ยังอาจมองไม่เห็น: รอบนี้พบ glyph ลูกศรมีขนาด 0×0 หลังเปลี่ยน wrapper เป็น `display:block` ต้องตรวจภาพจริงและแก้เป็น `inline-grid` ไม่ใช่เช็กเพียงว่า DOM มี icon
- ข้อมูล badge ยาวต้องมี display label ที่เหมาะกับพื้นที่ โดยรักษาค่า filter เดิมและชื่อเต็มสำหรับ accessibility ไม่ปล่อยให้บางการ์ดสูงเพิ่มทั้งแถว

### ขั้นตอนตรวจที่ต้องทำเอง

1. แยกภาพ Desktop/Mobile ของต้นแบบออกจาก device frame โดยไม่ยืดหรือ retouch เนื้อหา ระบุว่าสเกลใดมาจากการประมาณ
2. เปิดภาพ render ทั้งสองขนาดด้วย image viewer ทุกครั้งที่ตัดสินความใกล้เคียง งานทั้งหน้าดู overview แล้วดูส่วนบน กลาง ล่างที่ขนาดอ่านได้จริง
3. จดช่องว่างที่เห็นเป็นเรื่องเฉพาะ เช่น map ต่ำเกินไป chip หนาไป หรือภาพไม่มีแสง/จุดสนใจตามแบบ แล้วลงมือแก้ก่อนส่งผู้ใช้
4. หลังแก้ เปิดภาพใหม่ทั้ง Desktop/Mobile อีกครั้ง ภาพจากก่อนแก้ไม่ใช่หลักฐานของสถานะล่าสุด
5. แยกสิ่งที่แก้ได้ด้านดีไซน์ออกจากข้อจำกัดจริง เช่น reference มีข้อมูลตัวอย่าง แต่ runtime ต้องแสดง 12/6 รายการและ timeline ครบตาม handoff ห้ามตัดข้อมูลจริงเพื่อให้ความสูงตรงรูป
6. รายงานว่าเปิดดูอะไรจริง และเหลือความต่างอะไร ห้ามเขียนว่าผ่าน 90% จากการที่ test เขียวหรือไม่มี overflow

งานเล็กตรวจเป็น crop พร้อมเพื่อนบ้านทั้งสองขนาดได้ ไม่ต้อง build/test ทั้งเว็บไซต์ทุกครั้ง หลักฐานของรอบ Planner: [visual refinement review](planner-visual-refinement.md)
