# หน้ารายละเอียดวัน: บริบท ผลลัพธ์ และที่มาข้อมูล

จัดทำ 20 กันยายน 2026 สำหรับ ChatGPT วิเคราะห์ redesign ไม่ใช่การรับรองปฏิทินหรือผลทางโหราศาสตร์ และไม่มีการเปลี่ยน application code ในงานนี้

## 1. ขอบเขตและลำดับหลักฐาน

- Surface: `https://mongkolwela.vercel.app/calendar/day/`
- วันที่อ้างอิง: `?date=2026-09-20` หรือ 20 กันยายน 2569 ให้ล็อก query นี้เมื่อเทียบภาพ เพราะ URL ที่ไม่มีวันที่เปลี่ยนตามวันในเครื่องผู้ใช้
- **FACT:** ข้อเท็จจริงที่เห็นใน production หรืออ่านได้จาก source ที่ระบุ
- **INFERENCE:** การตีความ UX จากภาพ/โครงสร้าง ยังไม่มีผลวิจัยผู้ใช้รองรับ
- **REC:** ข้อเสนอ ไม่ใช่สิ่งที่ระบบทำอยู่แล้ว
- **UNKNOWN:** ยังไม่ตรวจหรือไม่มีหลักฐาน อย่าตีความเป็นผ่านการตรวจแล้ว

ภาพผู้ใช้และภาพ production เป็นหลักฐานหน้าตา; source เป็นหลักฐาน logic ฝั่ง local; CI รวมเป็นหลักฐานอัตลักษณ์ การตรวจนี้ไม่ได้พิสูจน์ว่า production ทุกไฟล์ตรงกับ local commit ทุกบรรทัด หากภายหลังพบต่างกันให้แจ้ง ไม่เลือกข้างเงียบ ๆ

เอกสารอื่นในชุด: `01-CHATGPT-PROMPT.md`, `03-BRANDING-AND-CI.md`, `04-CALENDAR-PAGE-DESIGN-NOTES.md` ภาพและโลโก้อยู่ใน `assets/`

## 2. หน้านี้อยู่ตรงไหนของ product

มงคลเวลาเน้นค้นหาวัด/สถานที่มงคลและวางแผนไหว้พระ ปฏิทินเป็นเครื่องมือเสริม ช่วยดูวัน จันทรคติ วันพระและคำแนะนำเบื้องต้น ไม่ควรทำให้ redesign หน้านี้เปลี่ยน positioning ของทั้งเว็บเป็นบริการทำนายชีวิต

เส้นทางหลัก: navigation วันพระ/ปฏิทินไทย → ปฏิทิน → รายละเอียดวัน → เปลี่ยนวันหรือกลับปฏิทินปีเดิม ข้อมูลวันอ่านได้โดยไม่กรอกวันเกิดหรือสมัครสมาชิก

**INFERENCE: งานของผู้ใช้ที่ควรใช้เป็นสมมติฐานออกแบบ** คือยืนยันว่าวันที่กำลังดูคือวันใด เป็นวันพระ/วันสำคัญหรือไม่ อ่านคำแนะนำโดยเข้าใจข้อจำกัด และเปรียบเทียบวันใกล้เคียง ไม่ใช่เปิดหน้ามาเพื่ออ่านวงโหรขนาดใหญ่เสมอไป

| Day navigation | วันก่อนหน้า, กลับปฏิทินปี, วันถัดไป | เป็นลิงก์จริง มี URL วันที่และปีที่เหมาะสม |

| Day wheel | SVG “จักรวันและดิถี” มีวง/เส้นแบ่งและ marker 4 ตัว | อธิบายว่าเป็น schematic; ความหมายไม่เท่ากับตำแหน่งดาวจริง |

| Advice | รายการ “คำแนะนำวันนี้” 3 ข้อ | เป็น template ตามวัน ไม่ใช่ personalized recommendation |

## 4. Data flow จริง

```text
Astro page + BaseLayout
  → <main data-calendar-day-detail> เริ่มต้นว่าง
  → thai-calendar-day.js ทำงานใน browser
  → อ่าน query date ผ่าน parseIsoDate หรือใช้ new Date()
  → createThaiDayInfo(date) จาก thai-calendar-core.js
  → ข้อมูลวัน/จันทรคติ/events/dithi/floating day
  → ประกอบข้อความ + SVG + navigation links
  → ใส่ HTML ลงใน main และอัปเดต document.title
```

**FACT:** ผลรายละเอียดวันถูกสร้าง client-side ไม่ใช่ SSR รายละเอียดวันที่ไว้ใน HTML ตั้งต้น ถ้า script ไม่ทำงาน main ส่วนนี้ไม่มีผลลัพธ์ดังกล่าว การปรับ loading/error/no-JS เป็นงานที่ต้องกำหนดเพิ่ม ไม่ใช่ state ที่พิสูจน์ว่ามีแล้ว

**FACT:** `thai-calendar-provider.js` มี provider สำหรับ CalenOS และ fallback แต่หน้ารายละเอียดวันนี้เรียก `thai-calendar-core.js` โดยตรง ไม่ได้ใช้ provider นั้น จึงห้ามเขียนว่า “ข้อมูลหน้านี้ดึงจาก CalenOS” หรือเชื่อม ephemeris แล้วเพียงเพราะพบไฟล์ provider ใน repo

**FACT:** ผลวันที่ในเส้นทางนี้ไม่ได้มาจาก CMS วัด ฐานทะเบียนวัด ข้อมูลผู้ใช้ หรือ model AI และไม่มี request API ปฏิทินใน page module ที่ตรวจ

## 5. ข้อมูลแต่ละประเภทมาจากไหน

### 5.1 วันที่และระบบศักราช

- อ่าน `date=YYYY-MM-DD` เป็น ค.ศ.; แสดงวันที่หลักเป็น พ.ศ. โดยบวก 543
- ถ้าไม่มีวันที่หรือ parser คืน null ใช้ `new Date()` ใน browser จึงขึ้นกับวันที่ local ของเครื่อง ไม่ได้กำหนด Asia/Bangkok สำหรับ fallback นี้โดยตรง
- parser แยก year/month/day แล้วสร้าง `new Date(year, month - 1, day)`; ไม่มี strict validation ของวันที่จริง จึงมีโอกาส rollover วันที่เกินเดือน
- จ.ศ. ใช้จุดเปลี่ยน 13 เมษายน; ม.ศ. = ค.ศ. - 79; ร.ศ. = พ.ศ. - 2325
- ปีนักษัตรเป็น lookup 12 สัตว์และจุดเปลี่ยนที่กำหนดเป็น 13 เมษายนใน code
- ค่าดังกล่าวเป็น convention ของ implementation ไม่ใช่หลักฐานว่าถูกต้องสำหรับทุกยุค/สำนัก/ช่วงวันที่

### 5.2 จันทรคติและวันพระ

- ใช้รอบจันทรคติเฉลี่ย `29.530588853` วัน
- anchor คือ `2026-01-19 12:00 UTC` พร้อมเดือนจันทรคติเริ่มต้นที่กำหนดใน code
- แปลงองค์ประกอบวันที่เป็น UTC noon เพื่อคำนวณจำนวนวันจาก anchor แล้วหา lunation/lunar age/ขึ้นแรม
- เดือนและประเภทปีใช้กฎรอบ 19 ปีแบบ modular ที่กำหนดไว้ใน code แยกปกติมาส อธิกมาส และอธิกวาร
- วันพระถูก flag จากวันจันทรคติ เช่น 8 ค่ำ ขึ้น 15 ค่ำ และวันท้ายของข้างแรมตาม logic
- ไอคอนดวงจันทร์เป็นรูปแบบ CSS ตามประเภท phase ไม่ใช่ภาพ illumination ที่คำนวณทางกายภาพ

**UNKNOWN:** งานนี้ไม่ได้ cross-check ปฏิทินจันทรคติกับฉบับทางการ/ฉบับโหรที่มีลิขสิทธิ์หรือ ephemeris จึงยังระบุ error rate, ความแม่นยำ หรือช่วงปีที่รับรองไม่ได้ การมีตัวเลือกปีหลายปีไม่พิสูจน์ความแม่นยำของสูตรตลอดช่วง

### 5.3 วันหยุดและเทศกาล

- รายการวันสุริยคติ hardcoded เช่น ปีใหม่ จักรี สงกรานต์ 13-15 เมษายน แรงงาน วันเฉลิมพระชนมพรรษา วันแม่ วันพ่อ รัฐธรรมนูญ และสิ้นปี
- รายการจันทรคติ hardcoded เช่น มาฆบูชา วิสาขบูชา อาสาฬหบูชา เข้าพรรษา ออกพรรษา และสารทไทย
- เพิ่มป้ายวันพระเมื่อผล lunar ตรงเงื่อนไข
- ไม่พบระบบ feed วันหยุดพิเศษ/ชดเชยราชการอัปเดตอัตโนมัติใน function ที่ใช้

ดังนั้น “ไม่มีวันหยุดหรือเทศกาลหลัก” เป็นผลของรายการที่ระบบมี ไม่ใช่การยืนยันว่าไม่มีเหตุการณ์หรือวันหยุดอื่นจริง

### 5.4 ดิถีและคำแนะนำ

`getDithiMarkers` ใช้กฎ/lookup วันในสัปดาห์ เดือน และดิถี สำหรับดิถีพิฆาต วันทรธึก ดิถีเรียงหมอน กระทิงวัน และอัคนิโรธ ส่วนวันลอย/วันฟู/วันจมใช้ชุดวันในสัปดาห์ที่กำหนดไว้

- `getGoodReadings`: เลือกกฎกลุ่ม auspicious/power เพิ่มวันพระ/วันลอยหรือฟูตามเงื่อนไข หรือใช้ข้อความทั่วไปเมื่อไม่มีรายการ
- `getAvoidReadings`: เลือกกฎกลุ่ม avoid/watch เพิ่มวันจม และจำกัดผลสูงสุด 4 รายการ
- `getAdvice`: template 3 ข้อ ใช้วันในสัปดาห์และชื่อดาวประจำวันแทรกในข้อแรก อีกสองข้อเป็นคำแนะนำทั่วไป
- “อัคนิโรธ” ถูกเพิ่มจากกฎเสมอใน implementation ที่ตรวจ ไม่ใช่เหตุการณ์ผิดปกติที่ตรวจพบจาก sensor หรือแหล่ง real-time
- การมีศัพท์ตำราใน note ไม่ใช่ citation ที่ระบุผู้แต่ง ฉบับ ปี และหน้า งานนี้ไม่พบหลักฐานในหน้าเพียงพอที่จะกล่าวว่าสูตรได้รับการรับรองจากแหล่งนั้น

**ประเด็นทบทวนข้อมูล ไม่ใช่การแก้ UI ในงานนี้:** วันเสาร์อยู่ทั้งชุดวันฟูและวันจม แต่ `.find()` เลือกชุดที่พบก่อน การเปลี่ยนลำดับหรือสูตรต้องแยกให้เจ้าของข้อมูลตรวจ ไม่ควรแก้ผ่าน redesign

### 5.5 วง “จักรวันและดิถี”

| องค์ประกอบ | Logic ที่ใช้จริง | ไม่ควรสื่อว่าเป็น |
| --- | --- | --- |
| วง 12 ส่วน | label จากชื่อเดือนสุริยคติไทย ตัด 3 ตัวอักษร | การคำนวณเรือนชะตา/ราศี |
| marker อา | มุมคงที่ 15 องศา | ตำแหน่งดวงอาทิตย์ตามวันที่ |
| marker จ | `lunar.tithi / 30 × 360` | ตำแหน่งดวงจันทร์ ephemeris |
| marker ว | `weekday × 360 / 7` | ตำแหน่งดาวอีกดวง |
| marker เลขไทย | หมายเลขปีนักษัตร × 30 องศา | สมผุสดาวหรือดวงชะตาส่วนบุคคล |
| ตัวกลางวง | เลขวันจันทรคติและขึ้น/แรม | คะแนนความมงคล |

เป็น SVG static ที่มี accessible name ระบุแผนภาพวัน ยังไม่มีคำอธิบายความหมาย marker แบบละเอียดหรือ legend ใน page module **การ redesign ที่ทำวงให้ดูละเอียด/วิทยาศาสตร์ขึ้น โดยไม่เปิดเผยวิธีสร้าง จะเพิ่มความน่าเชื่อถือเกินหลักฐาน**

## 6. ผลตัวอย่างที่ตรวจบน production

วันที่ล็อกสำหรับภาพคือ **2026-09-20**:

| รายการ | สิ่งที่เว็บแสดง |
| --- | --- |
| วันที่ | 20 กันยายน 2569, อาทิตย์ |
| จันทรคติ | ขึ้น ๙ ค่ำ เดือนสิบ (๑๐) |
| ปี | มะเมีย, ปกติมาส |
| ศักราช | จ.ศ. 1388, ม.ศ. 1947, ร.ศ. 244 |
| Event | ไม่มีวันหยุดหรือเทศกาลหลัก |
| เกื้อหนุน | ข้อความทั่วไปให้เตรียมข้อมูลและไม่เร่งเกินจังหวะ |
| ควรหลีกเลี่ยง | อัคนิโรธเกี่ยวกับที่ดิน/ขุด/ถม/ปลูกเรือน และวันจม |
| คำแนะนำ | 3 ข้อจาก template โดยข้อแรกผูกกับวันอาทิตย์ |

ข้อ “วันจม” ในกล่องหลีกเลี่ยงกลับอธิบายว่างานเก็บ ปิดบัญชี คุมคน หรือสะสางของเก่าเหมาะกับวันนั้น เป็น **ความไม่ตรงกันระหว่างหัวข้อหมวดกับเนื้อหา** ที่ควรให้เจ้าของกฎพิจารณาก่อนปรับภาษา

ได้กดวันถัดไปบน production: URL เปลี่ยนเป็น `?date=2026-09-21` และ heading เป็น 21 กันยายน 2569 ผลวันเปลี่ยนเป็นจันทร์/ขึ้น 10 ค่ำ จากนั้น browser back กลับมาวันที่ 20 ได้ การตรวจนี้พิสูจน์ navigation ตัวอย่าง ไม่ได้พิสูจน์ความถูกต้องของทุกวันที่คำนวณ

## 7. Product contracts ที่ต้องรักษา

1. URL วันที่เป็น ค.ศ. ISO แต่ display เป็น พ.ศ.; อย่าส่ง พ.ศ. เข้า query แทน ค.ศ.
2. วันก่อนหน้า/วันถัดไปต้องเดินข้ามขอบเดือนและปีตามวันจริงได้ ไม่บวกเลขในข้อความอย่างเดียว
3. กลับปฏิทินปีต้องใช้ปีของวันที่เลือก ผ่าน `../?year=<BE>` ไม่ใช่ปีปัจจุบันเสมอ
4. H1, breadcrumb, document title, facts, event, advice และวงต้องผูกกับวันเดียวกัน
5. แยก “วันที่เลือก” จาก “วันนี้”; อย่าบอกคำแนะนำเป็นของวันนี้เมื่อผู้ใช้เปิดวันอื่น
6. รักษาข้อมูลที่มีและข้อจำกัด แม้จะจัดลำดับ/ทำ progressive disclosure ใหม่
7. ไม่สร้าง personalized reading, API, คะแนน หรือช่วงฤกษ์เพิ่มโดยอ้างว่าเป็นเพียงการจัดหน้า
8. ไม่กระทบเส้นทางปฏิทินปี หน้า planner หรือ shared consent/menu; เปลี่ยน component ร่วมต้องแยกขอบเขตและตรวจผู้ใช้ร่วม

## 8. State matrix สำหรับการออกแบบต่อ

| State | สถานะหลักฐาน | สิ่งที่ต้องคำนึง |
| --- | --- | --- |
| วันทั่วไปตัวอย่าง | เห็นจริงบน production | วันที่, facts และคำแนะนำอ่านได้ชัด |
| เปลี่ยนวัน + browser back | ทดสอบจริงหนึ่งคู่วัน | URL และเนื้อหาต้องตรงกัน |
| วันพระ/หลายเทศกาล | รองรับใน source, ไม่ได้ capture ในรอบนี้ | ป้ายหลายรายการไม่ชนหัวข้อหรือ facts |
| ข้ามเดือน/ปี | logic ใช้ Date, ยังไม่ได้ UI test ในรอบนี้ | back-to-year และทุก field ต้องปรับตาม |
| วันที่ไม่ถูกต้อง | พบ parser ไม่ strict | ต้องออกแบบ validation/recovery หากแก้ logic หรือเพิ่ม picker |
| Script ยังไม่ทำงาน/ล้มเหลว | main เริ่มว่างใน source | fallback/status เป็นงานที่ต้องกำหนดเพิ่ม |
| Desktop | capture 1280×720 | มีภาพ 4 ช่วงครอบคลุมหน้า |
| Mobile/zoom/keyboard | อ่าน responsive CSS เท่านั้น | ยังไม่ผ่าน visual/interaction QA ในงานนี้ |

## 9. ประเด็น UX สำหรับ ChatGPT วิเคราะห์ต่อ

ทั้งหมดต่อไปนี้เป็น **INFERENCE/REC ไม่ใช่ข้อสรุปจาก user research**:

- ขนาด hero และวงทำให้ข้อมูลใช้งานจริงอยู่ต่ำ ควรเปรียบเทียบลำดับ “วัน → เหตุการณ์ → คำแนะนำ → รายละเอียดเพิ่มเติม” กับของเดิม
- ข้อมูลซ้ำใน hero, lunar panel และกลางวง อาจย่อจุดซ้ำโดยไม่ลดความเข้าใจ
- ฝั่ง facts ถูกยืดสูงตามวง ทำให้มีพื้นที่ว่างมากในวันไม่มี event; ไม่ควรเติมเนื้อหาเทียมเพื่อถมที่ว่าง
- ข้อจำกัดสำคัญอยู่ท้ายหน้าและใช้ภาษาทาง implementation อาจทำ summary ใกล้ผลและเก็บรายละเอียดแหล่งข้อมูลให้เข้าถึงได้
- สีและศัพท์มีน้ำหนักเชิงอำนาจ ควรระวังไม่ให้ดูเป็นผลคำนวณที่แม่นยำหรือคำสั่งห้ามเด็ดขาด
- แยกสิ่งที่ “เหมาะทำ” กับ “ควรระวัง” จากความหมายจริง ไม่จัดหมวดตามชื่อกฎเพียงอย่างเดียว
- เพิ่ม date picker/วันนี้/บันทึก/เชื่อม planner ได้เฉพาะในฐานะข้อเสนอใหม่ที่ต้องอนุมัติ ไม่ใช่ missing feature ที่ต้องทำทันที
