# Prompt สำหรับ ChatGPT: redesign หน้ารายละเอียดวันของมงคลเวลา

## วิธีใช้ชุดนี้

แนบไฟล์ `02-PAGE-CONTEXT-AND-DATA.md`, `03-BRANDING-AND-CI.md`, `04-CALENDAR-PAGE-DESIGN-NOTES.md` และภาพใน `assets/` ให้ ChatGPT แล้วส่งข้อความตั้งแต่หัวข้อ “เริ่ม prompt” ด้านล่าง หากแนบได้ไม่ครบ ให้เริ่มจาก 02, 04 และภาพเต็ม `calendar-day-user-reference.png` ก่อน

ภาพ `calendar-day-production-desktop.png` เป็น contact sheet จากหน้าจอ production 4 ช่วง ไม่ใช่ภาพ layout ต่อเนื่อง ห้ามตีความเส้นแบ่ง/ป้ายกำกับของ contact sheet เป็น UI เว็บไซต์ ไฟล์ภาพแต่ละช่วงและโลโก้จริงแนบมาด้วย

## เริ่ม prompt

คุณคือ senior product designer และ UX writer ที่เข้าใจเว็บไซต์ภาษาไทยและการนำเสนอข้อมูลความเชื่ออย่างรับผิดชอบ ช่วยวิเคราะห์และเสนอ redesign **เฉพาะหน้ารายละเอียดวัน** ของเว็บไซต์มงคลเวลา:

- หน้าปกติ: https://mongkolwela.vercel.app/calendar/day/
- วันที่อ้างอิงให้ตรงกับภาพ: https://mongkolwela.vercel.app/calendar/day/?date=2026-09-20
- ชื่อแบรนด์: มงคลเวลา / Mongkol Wela
- เป้าหมายแบรนด์หลัก: คู่มือค้นหาวัดและสถานที่มงคล พร้อมวางแผนไหว้พระ ไม่ใช่การเปลี่ยนทั้งเว็บให้เป็นบริการทำนายชีวิต
- บทบาทหน้านี้: เครื่องมือเสริมสำหรับอ่านวันที่ จันทรคติ วันพระ/วันสำคัญ และคำแนะนำตามกฎความเชื่อเบื้องต้น

อ่านเอกสารแนบก่อนเสนอดีไซน์ แยกข้อเท็จจริงจาก codebase, สิ่งที่เห็นในภาพ, สมมติฐาน UX และข้อเสนอของคุณ อย่าอ้างว่าได้ทำ user research หรือยืนยันความถูกต้องของปฏิทินแล้ว

### เรื่องสำคัญที่ต้องเข้าใจก่อนออกแบบ

1. หน้านี้คำนวณจาก JavaScript ฝั่ง browser ด้วยรอบจันทรคติเฉลี่ยและกฎที่กำหนดไว้ใน code ยังไม่ได้ใช้ฐาน ephemeris หรือปฏิทินโหรฉบับตรวจสอบได้ในเส้นทางการทำงานของหน้านี้
2. แผนภาพ “จักรวันและดิถี” เป็นภาพเชิงสัญลักษณ์จากค่าที่ระบบกำหนด ไม่ใช่ตำแหน่งดวงอาทิตย์/ดวงจันทร์/ดาวที่คำนวณทางดาราศาสตร์ ห้ามออกแบบให้ดูเป็นหลักฐานความแม่นยำที่ไม่มีอยู่
3. คำแนะนำมาจากกฎและ template ไม่ใช่คำทำนายเฉพาะบุคคล ไม่มีการรับวันเวลาเกิด และไม่มีช่วงฤกษ์ระดับชั่วโมง/นาที
4. วันหยุด/เทศกาลมาจากรายการและกฎใน code ไม่ใช่ feed วันหยุดราชการที่อัปเดตอัตโนมัติ “ไม่มีวันหยุดหรือเทศกาลหลัก” หมายถึงไม่พบในรายการของระบบเท่านั้น
5. ค่าในภาพ 20 กันยายน 2569 เป็นผลที่เว็บแสดง ไม่ใช่ข้อมูลที่ผู้จัดทำ brief รับรองว่าแม่นยำแล้ว
6. ต้องคงความหมายของข้อจำกัดและที่มาข้อมูลไว้ จะย่อหรือย้ายให้เข้าใจง่ายขึ้นได้ แต่ห้ามซ่อนจนผู้ใช้เข้าใจว่าระบบเป็นแหล่งฤกษ์ทางการ

### งานที่ต้องการจากคุณ

1. สรุปหน้าที่หลักของหน้านี้และสิ่งที่ผู้ใช้ควรเห็น/ทำได้ก่อน โดยให้ “อ่านวันและเข้าใจข้อมูล” สำคัญกว่าการตกแต่ง
2. วิเคราะห์แต่ละส่วน: header, วันที่และ navigation, ข้อมูลจันทรคติ, แผนภาพ, ข้อมูลเกื้อหนุน/ควรระวัง/คำแนะนำ, ที่มาข้อมูล และ footer ระบุว่าควรเก็บ ปรับ รวม ย้าย หรือลด พร้อมเหตุผลและ tradeoff
3. เสนอทิศทางดีไซน์ 2 แบบที่ยังเป็นมงคลเวลา แล้วแนะนำ 1 แบบ ไม่ต้องทำหลาย moodboard ที่ต่างแค่สี
4. เสนอ information hierarchy และ wireframe แบบข้อความสำหรับ desktop และ mobile ระบุว่าส่วนไหนอยู่เหนือ fold โดยใช้ขนาดตัวอย่างที่ชัดเจน
5. เสนอ typography, สีตามบทบาท, spacing, ความหนาแน่น, ขนาดภาพวง และลักษณะข้อมูล โดยอ้างอิง CI จริงที่แนบ ไม่เปลี่ยนแบรนด์เป็น dashboard เทคโนโลยีหรือเว็บดูดวงเต็มตัว
6. เขียนตัวอย่าง microcopy ภาษาไทยสำหรับหัวข้อ navigation, สถานะวันสำคัญ, คำอธิบายแผนภาพ และข้อความความน่าเชื่อถือ ใช้คำว่า “วันที่เลือก” ให้ถูกเมื่อผู้ใช้ดูอดีต/อนาคต
7. เสนอว่าจะแสดงแผนภาพเดิมอย่างไรให้มีประโยชน์และไม่ชวนเข้าใจผิด หากแนะนำลด/ย้าย/แทนที่ ต้องบอกว่าจะรักษาข้อมูลหรือคุณค่าที่มีอยู่อย่างไร ไม่ลบทิ้งเพราะดูต่างจาก component อื่นเฉย ๆ
8. ระบุ states ที่ควรออกแบบ: วันทั่วไป, วันพระ, วันสำคัญหลายรายการ, รายการคำแนะนำยาว, ข้ามเดือน/ปี, วันที่ไม่ถูกต้อง และหน้าจอเล็ก รวมถึงการเข้าถึงด้วย keyboard และ screen reader
9. จัดลำดับสิ่งที่ควรทำก่อน พร้อมแยก **ปรับดีไซน์/ภาษาได้ด้วยข้อมูลเดิม**, **ต้องตรวจสูตรหรือแหล่งข้อมูล**, และ **ฟีเจอร์ใหม่ที่ต้องขออนุมัติ**

### ขอบเขตและสิ่งที่ห้ามสมมติ

- คงเส้นทาง `/calendar/day/?date=YYYY-MM-DD`, ลิงก์วันก่อนหน้า/ถัดไป และกลับปฏิทินปีที่เลือก พ.ศ. ให้มีทางใช้งานชัดเจน
- อย่าเสนอให้เปลี่ยน Home, ปฏิทินทั้งปี, planner หรือ global navigation ไปพร้อมกัน หากพบผลกระทบ shared component ให้ระบุเป็นงานอีกขอบเขต
- ห้ามสร้างคะแนนความมงคล เปอร์เซ็นต์ความแม่นยำ สถานะ “รับรองแล้ว” ช่วงฤกษ์จริง หรือคำแนะนำเฉพาะบุคคลขึ้นมาเอง
- การเพิ่ม date picker, ปุ่มวันนี้, บันทึก/แชร์วัน, เชื่อมเข้า planner หรือ API ใหม่ เป็นข้อเสนอใหม่ ไม่ใช่ฟีเจอร์ที่มีอยู่แล้วในหน้านี้
- รักษาโลโก้จริง แดงชาด/เขียวหยก/ทอง/พื้นกระดาษ และน้ำเสียงสุภาพไม่รับประกันผล สี marker ในแผนภาพอาจเป็น functional variant ไม่ต้องบังคับให้ทุกสีเหมือนปุ่ม
- มีอิสระปรับสัดส่วนและลำดับเพื่อ usability แต่ระบุ tradeoff ห้ามตัดข้อมูลหรือเปลี่ยนความหมายของสูตรเงียบ ๆ
- ไม่ใช้ความกลัว เช่น “ห้ามทำเด็ดขาด ไม่เช่นนั้นเกิดเคราะห์” และไม่ทำให้ข้อมูลความเชื่อดูเป็นคำแนะนำทางการแพทย์ กฎหมาย หรือการเงิน

### รูปแบบคำตอบที่ต้องการ

เริ่มจาก diagnosis สั้น ๆ ตามด้วยตารางตัดสินใจรายส่วน, ทิศทางที่แนะนำ, wireframe desktop/mobile, ตัวอย่างภาษาไทย, ข้อกำหนด CI และรายการงานเรียงลำดับ ปิดด้วยคำถามเจ้าของโปรเจกต์เฉพาะเรื่องที่จำเป็นจริง ๆ

ในคำตอบแรก **ยังไม่ต้องเขียนโค้ดหรือทำ HTML** ให้เราเลือกทิศทางก่อน หากข้อมูลไม่พอให้ระบุว่าไม่ทราบ อย่าเติมรายละเอียดให้ดูเหมือนเป็นข้อเท็จจริง
